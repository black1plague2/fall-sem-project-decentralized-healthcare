How it works

Six real steps, not a demo timer

Everything below actually happens on the server when you use the dashboard — each step is streamed live so you can watch it, not just take it on faith.

01
Encrypt client-side
A fresh 256-bit key (CEK) is generated per file and used for AES-256-GCM authenticated encryption — tamper-evident, not just confidential.
02
Pin to IPFS
The encrypted package (never the plaintext) is content-addressed and pinned to IPFS. The CID is hashed and anchored, not the file itself.
03
Wrap the key per actor
The CEK is individually wrapped with RSA-OAEP for each authorized actor — Doctor, Hospital, Insurance — so no two actors share a copy of the same key material.
04
Anchor & share on Hydra L2
The permission record is anchored and proposed to a Hydra Layer-2 head for near-instant (5–15ms target) off-chain permission checks.
05
Verify on request
When an actor asks for access, the server checks Hydra L2 first, then falls back through Aiken L1 → Midnight ZK → Blockfrost L1 — cheapest and fastest layer first, most authoritative last.
06
Revoke rotates the key
Revoking an actor doesn't just delete a row: the file is re-encrypted under a brand-new CEK and re-wrapped for everyone remaining, so the old key is permanently useless.

Off-chain state channel. Near-physical-limit latency for permission checks — 100–400× faster than a base-layer query.

Actors

Built for four roles

Every permission decision is owner-controlled: the Patient grants and revokes, everyone else requests.

Patient
Owner
Uploads records, grants access, and is the only actor who can revoke it.
Doctor
Requester
Requests access to treat a patient; access is scoped to records they've been granted.
Hospital
Requester
Institutional access for admissions, records handling and coordination of care.
Insurance
Requester
Verifies claims against records it has explicitly been granted access to — nothing more.
